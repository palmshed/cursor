# Architecture

Cursor is organized around five top-level modules.

## Layout

| Module      | Location        | Responsibility                                                                |
| ----------- | --------------- | ----------------------------------------------------------------------------- |
| `app/`      | `src/app/`      | Startup, session lifecycle, command routing, menus                            |
| `core/`     | `src/core/`     | Runtime state, model catalog, metrics, shared domain types                    |
| `ui/`       | `src/ui/`       | Terminal rendering, markdown output, prompts, menus                           |
| `services/` | `src/services/` | Execution engine, AI, replay, Git, GitHub, CI, file and external integrations |
| `utils/`    | `src/utils/`    | Shared utilities and low-level helpers                                        |

---

## Entry Point

```text
main.cpp
  ↓
Agent
  ↓
app/
  ↓
services/
  ↓
ui/
```

`Agent` is a lifecycle coordinator.

Application decisions are made by the ExecutionEngine.

---

## Core Runtime Layers

### ExecutionEngine

The ExecutionEngine is the decision layer.

Responsibilities:

* goal classification
* investigation planning
* tool selection
* tool orchestration
* evidence collection
* completion gating
* outcome generation

The engine operates through an investigation loop:

```text
Goal
  ↓
Select Tool
  ↓
Execute Tool
  ↓
ToolResult
  ↓
Evidence
  ↓
Completion Gate
```

---

### Replay

Replay is the evidence layer.

Responsibilities:

* append-only event storage
* outcome recording
* recovery metrics
* trust metrics
* confidence tracking
* schema versioning

Replay is the source of truth for historical behavior.

Metrics are derived from replay events rather than maintained separately.

---

### AIService

AIService is a synthesis layer.

It does not investigate repositories.

It receives repository evidence generated by the ExecutionEngine and produces answers from that evidence.

```text
ExecutionEngine
  ↓
Evidence
  ↓
AIService
  ↓
Answer
```

Investigation and synthesis are intentionally separated.

---

## Runtime State

`SessionState` owns runtime state.

Examples:

* active model
* conversation state
* outcomes
* recovery metrics
* trust metrics

Session state should never contain provider-specific logic.

---

## Model Catalog

Model selection is data-driven.

`ModelCatalog` is the single source of truth for:

* providers
* models
* capabilities
* pricing tier
* categories
* display metadata

New providers and models are added through catalog entries rather than new enums or switch statements.

---

## Telemetry

Telemetry is a first-class architectural concern.

### ToolResult

Every tool execution produces a structured result:

```text
ToolResult
  tool
  args
  stdout
  stderr
  exit_code
  success()
```

### Tool History

Each investigation accumulates an ordered tool history.

```text
ToolHistory
  ↓
Evidence
  ↓
Replay
```

This allows investigation behavior to be analyzed after execution.

---

## Design Principles

### Separation of Concerns

* `app/` controls flow
* `core/` owns state and domain models
* `ui/` controls presentation
* `services/` provide capabilities
* `utils/` provide shared helpers

### Evidence Before Opinion

Repository evidence takes priority over model assumptions.

Investigation should happen before synthesis.

### Service-Oriented

Capabilities belong in services rather than orchestration code.

### Data-Driven Configuration

Providers, models, capabilities, and metadata belong in catalogs rather than enums and switch chains.

---

## Stability

The architecture prioritizes:

* reproducibility
* traceability
* deterministic execution
* evidence-based decisions
* minimal abstraction drift

New architectural layers require evidence from production traces.

Architecture changes should be justified by failure topology rather than speculation.

Current phase: Observation.
